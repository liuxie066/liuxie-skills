# PRDflow

把「用户希望达成什么」变成「用户怎样完成、系统按什么规则响应、怎样判断做成」。
先交付可阅读的需求草稿，经确认和核验后作为需求合同交接；不产出代码、数据库结构或通用平台。

## 起步：先识别当前请求

- 用户只想讨论方法或设计思路：停留在讨论，不直接生成完整方案或写文件。
- 用户带来尚未成形的需求：共同澄清目标、主线和边界；初步明确后主动呈现草稿，后续围绕草稿修改。
- 用户要求把已有讨论整理成 PRD：复用对话、已确认决定和相关证据，直接成稿，不要求提前启动本 skill 或重做访谈。
- 用户要求修订已有 PRD：更新同一份正文及受影响的规则、验收和决定状态，保留未受影响的共识。
- 用户要求收口、保存或交接：交付相应正文与状态，不把它当成开发授权。
- 如果在用业务案例设计 workflow/skill，同时保留「主任务」和「试跑任务」。
  试跑 PRD 完成不等于 skill 完成；业务实现也不自动成为当前任务。
- 先读取适用的项目约定；涉及既有产品行为时，沿当前入口查源码、配置和测试。
  区分当前实现、部署状态、用户的新要求，不从名字或旧文档猜功能。

成稿或修订前读取[产物与交接约定](references/delivery.md)。不要求用户选择模式或学习阶段命令。
局部未决项或证据缺口标在草稿对应位置，说明影响；它们阻止受影响结论确认和整体就绪，
不阻止先交付已知部分。目标本身不清楚时先澄清，不为了成稿编造需求。

## 代码现状门槛

既有项目在形成依赖现状的方案前，必须完成相关代码核查；不能等保存或开发时补做。
先明确问题，再从真实入口追踪到处理、数据读写和用户可见结果，核对相关配置及测试。
记录工作区、分支/提交、未提交差异、读过的关键路径、已有能力/缺口和未覆盖边界。
区分本地检出、所参照主线和部署版本；已有本地主线可比较，但未fetch不得称为远端最新。
源码与旧文档冲突时沿代码查证，不能重复建设已实现能力。承诺读取数据时，核实实际生产者
是否保留必要信息；没有真实样本时明确哪些只是源码证据，不自行访问生产或生成业务数据。

按[门槛记录与校验](references/gates.md)留下证据并执行`--phase code`。只列文件名、
搜索命中或复制文档不算读懂调用链。证据不足时，受影响判断保持未确认；不阻塞无关探索，
可保存标记缺口的草稿，但不得宣称整体方案可确认或可交接。
纯方法讨论不触发此门槛；无代码的新项目、非软件需求可有依据地记为不适用。
既有仓库不可访问属于阻塞，不能伪装成无代码。范围限于相关链路，不要求全仓审计。

## 多轮推进与共识

围绕一个决策点，可以解释、查证、举例和修正多轮，直到足够明确；
不规定轮数，不把每条消息当成新阶段，也不要求每轮走完一次 PRD 循环。

先回应用户当前输入，再决定是否推进：

- **询问或倾向**：解释或查证，不能当成确认；用户只求解释时不顺便推进新决定。
- **补充**：纳入相关场景，检查对主线、约束和验收的影响。
- **纠正**：替换受影响的方案及验收，保留其他共识与旧方案被替代的理由。
- **确认**：固化当前明确的决定，再选下一关键问题；「确认」「继续」只覆盖紧邻且清楚的待决范围。
- **改变目标**：指出目标/范围的变化及受影响决定；明确的新指令可更新共识，存在真实歧义才澄清。

解释后没有新决定，共识可以不变。产品选择的确认不自动授权写文件、启动 devflow 或外部操作。

在现有会话或需求文档持续维护四项信息，不创建状态管理工具：

1. **目标与范围**：目标用户、困难、成功信号、非目标、已知变化场景及当前授权。
2. **已确认决定**：当前有效选择；已被替代的方案不能继续混入规范。
3. **当前建议及依据**：正在讨论什么、哪些是事实/推断/假设、还缺什么证据。
4. **关键未决问题**：只保留影响目标、主线或验收的缺口，邻近改进留在范围外。

新决定必须能说明它服务哪个目标或已知场景。一般推进一个关键决策点，相关问题可合并；
不能从头重问已有答案，也不为保持对话而制造新问题。无关键产品缺口时按下文收口。

决定变化时同步修订当前草稿，按需简短说明变化；普通解释轮不重复整份 PRD。
首次形成草稿，以及用户要求成稿、整体收口或继续完成已承诺的整理时，交付可独立阅读的完整正文，
不只报告能力清单、验收摘要或“下一步再整理”。已有保存授权时更新并链接同一文档；
否则在最终回复呈现会话版正文，不能只把正文留在工具调用或校验输入里。
恢复上下文先读最新共识及确认依据；只有关键决定无法核实时才向用户补问。

## 工作循环

按需要循环，不把每一步都变成固定问卷或人工关卡：

### 抽象需求

提炼用户的任务、约束和成功标准。区分「首个具体案例」与「承诺支持的变化范围」。
可以先覆盖一个真实任务，但不能把用户已明确提出的第二个任务砍掉，再声称产品具有通用能力。
没有已知变化需求时，不为假想未来设计平台。
区分第二场景是用于验证变化能力，还是用户已承诺的首版交付项；不把所有已知案例
自动升级为首版必须全部上线，也不擅自砍掉已承诺能力。

遇到「沿用、参考、一致」时，明确复用的是流程、公式、参数、排序还是交互；
不要把一个维度的对称性默认为所有维度都一致。目标是否一致比形式对称更重要。

### 保留已有技术约束

综合讨论或交接时，保留已经明确且会影响产品行为的技术决定，例如已确定的 API 返回语义、数据保留限制或兼容约束。逐项写明约束、确认或核查依据、影响的用户行为与验收；区分用户已确认的决定、代码核实的现状限制和未确认建议。实现现状不自动成为必须沿用的产品要求，旧决定被明确替代时不继续混入有效约束。

只记录当前讨论中已有的决定，不借此新增模块、数据库结构或实现切片。不影响产品行为的代码细节留给 Devflow；影响行为的既定契约需要精确字段或简短片段才能表达时，可保留最小必要内容并注明来源和状态，不扩成实现方案。约束与产品目标冲突时说明影响并返回产品取舍，不默默削弱目标或丢弃约束。

### 验证依据

在会改变方向的重要判断前，检查是否需要外部参考：

- 用户问「最佳实践」「优秀产品怎么做」时查真实一手资料；重点看解决机制与取舍，
  不堆竞品功能或把教程参数称作行业统一最优值。
- 把结论分为：直接证据、由证据推断、适用于本需求的建议、待验证假设。
- 链接应能直接支持结论；当前实现用当前源码验证，研究建议不能伪装成已验证效果。
- 无法取得资料时说明缺口，不补造引用。缺口只阻塞依赖它的判断，不阻塞无关工作。
- 仅当某个不确定性会改变产品决定时提出最小验证实验，不自动扩展成回测或研究平台。

### 具象交互

用一个具体输入沿主线走一遍：触发 → 用户看到的信息 → 用户操作 →
系统动作 → 可见结果 → 完成/退出。已有界面、命令或通知入口能承载时先复用。
纯后台或数据需求用事件与结果表达，不强造 UI。

检查实际相关的分支：多入口、部分完成、没有结果、证据缺失、重复事件、
中途退出和新规则如何影响存量。不要给每个产品强加同样的状态机。

涉及保存、纠正、删除、取消、重试或跨会话继续时，必须用相关的跨时间场景检查：
首次操作 → 修改/中断 → 再次进入 → 最终可见结果；明确哪些旧结果不得重新出现。
覆盖本需求已承诺的不同状态变化，不能随便选一条简单场景替代关键语义。
无持久状态时说明不适用即可，不强造恢复功能。数据库、事务、锁和实现机制留给devflow。

三类合同：

- 数据：定义、单位、计算口径、唯一依据、时间/有效性、缺失和冲突处理。
- 判断：目标、硬约束、排序/优先级、阈值依据、冲突时谁优先、无解时怎么办。
- 动作：谁触发、谁有权确认、影响范围、副作用、失败/重试/终止后的行为。

预测、情景值、实际结果分开；同一事实不能重复计入。把操作文案当成行为合同，
例如「开始监控」不能隐含下单或把后续交易自动归属到这个任务。

### 收敛到最小可交付需求

删除不服务目标或已知变化场景的功能；保留正确性、用户明确要求和闭环所需能力。
按用户可完成的行为描述首版，不以文件数、模块清单、代码量代替交付。

每次收敛回到目标锚点检查：

1. 首个真实任务是否可以完整完成并看见结果？
2. 已知第二种不同场景是否仍被覆盖？没有第二种已知场景就不虚构。
3. 数据、策略、动作是否互相一致？有没有为迁就方案改写原目标？
4. 此轮是否改变了用户批准的范围、成本、权限或不可逆行为？

有偏差按多轮推进约定处理，不为迁就方案重写目标或削弱验收。

## 收口与停止发散

整体确认或标记可交接前，执行同一收口节点内的检查，不增加用户审批轮次：

1. 核对正文能解释本次产品行为具体改变什么，再走完首个任务及已知不同场景，检查入口、动作、结果、失败/退出；章节齐全或验收清单齐全不算通过。
2. 每项核心验收写明输入、可观察通过条件、证明方法、所需环境、模拟边界和前置条件。
   证明方法具体到从哪个用户入口触发、在哪里观察结果；优先引用已核查且能证明行为的页面、命令、API 或集成测试入口及相似测试。说明现有入口能证明什么、还缺什么；“运行测试”不算完整方法。入口无法核实时标待核验，新功能尚无入口时描述计划中的行为边界，不虚构路径或命令、不为产品阶段新建测试框架。记录既有入口是证据引用，不冻结未来文件布局、函数或 mock 设计。
   产品阶段要求证明计划完整，不要求提前实现或调用真实服务；未执行与执行失败分开，
   模拟测试不能替代真实模型质量/外部效果证据，不擅自创造指标、预算或操作授权。
3. 核对跨时间场景、数据可用性和会改变方向的研究依据；已有证据能补齐的直接补齐，
   产品取舍才提问。不得为填章节强制竞品调研。
4. 对当前完整需求做内容评审，记录证据、缺口及裁决，随后执行`--phase ready`。
   有实质缺口先补齐再复核；无法评审或校验失败不能当无问题，不因用户只说“继续”放行。

满足以下条件才建议整体收口，不继续挖掘假想场景：

- 目标、范围、用户主线、关键例外和成功/退出条件可解释。
- 影响验收的数据、策略、权限和存量行为已决定；影响当前结论的阻塞项均已关闭。
- 首个任务和已知变化案例都有可观察验收；重要取舍有理由。
- 未决技术问题可交由实现设计解决；会改变产品结果的问题不能伪装成技术细节。

[门槛记录与校验](references/gates.md)规定记录格式、程序校验和内容评审的不同责任。
脚本exit 0仅说明记录完整且版本一致，不能证明阅读或推理正确。当前skill没有宿主状态机；
这是要求执行的交接门槛，不宣称能阻止任意agent绕过。接收方应复验记录而不只接受口头“通过”。

整体确认已有答案；只突出新增未决点，不重新确认全部内容。
称「需求已确认」不代表收益最优、实现已完成或测试已通过。

## 保存与 devflow 交接

保存、更新或准备交接前完整读取 [产物与交接约定](references/delivery.md)。
尊重用户指定位置和当前 canonical owner；未经保存请求，默认在会话里共创。
不以目标 PRD 覆盖标记为「已实现」的现状文档，也不创建 final/v2 等平行真源。

prdflow 结束于产品需求和交接材料：

- 读取接收方当前可用的 devflow 约定以确定入口，但不因此运行 workflow。
- PRD 是产品输入，不是 devflow 的 implementation design，也不是 Save Design 完成。
- 「准备交接」不授权启动 devflow、评审、实现、提交、发布或部署。
- 用户明确启动 devflow 后，按接收方当前流程核实实现事实、准备实现方案；
  已确认需求作为输入保留，不跳过其确认门，也不无故重做需求访谈。
- devflow 不可用时仍交付自包含需求及待执行动作，不自动安装其他 skill。
- 在交接中提供门槛校验命令、结果及同版本内容评审引用；代码或需求变化后重验受影响结论，
  重新绑定记录，不直接刷新hash冒充重读。不能把产品已确认、技术实现、本地验证、真实效果验收混为完成。
- 在最终回复给出文档位置、真实验证、未决项和下一条未获授权的动作。

## 验证这个 skill

改动本 skill 时，用 [行为用例](evals/evals.json) 检查实际响应，不以标题或关键词匹配代替行为判断。
至少区分目标偏移、首案例定制、证据不足与准备交接越权；还应盲测未经提醒的主流程缺口、
旧代码事实、真实生产者缺字段、模拟证据冒充效果，以及跨时间状态冲突。
用无状态的小需求验证不会强加代码库、研究或状态机；脚本拒绝测试和agent行为测试分开报告。
修改多轮规则时执行其中的连续对话用例：同一 agent 接收逐轮消息，不预读后续输入或期望答案；
观察中途回应与最终共识，不把若干无上下文单轮回答或整段会话总结称作多轮测试。
同时用非首个业务领域的场景检查泛化，记录实际响应、失败及修正后的回归范围。
结构校验只说明文件合法；没有实际试跑不得宣称行为测试通过。
