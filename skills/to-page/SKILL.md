# To Page

把业务需求变成可以讨论、实现和验证的页面结构。先回答“用户如何完成任务”，再决定界面如何承载它。默认交付结构方案；用户已要求实现时，在其范围内继续，不人为增加审批节点。

## 起步：从已有讨论与源码现状接续

输入优先来自当前可访问的聊天记录、已确认决定、已有结构稿和相关源码；不要求用户先填需求表、提供 PRD 或从头介绍项目，也不要求讨论开始时就启动本 Skill。无法访问的其他会话不假装已读。

- 只讨论问题或解释思路时，先回应当前问题，不自动写完整方案或改代码。
- 用户要求“结合刚才讨论整理页面”时，直接提炼有效共识、核对源码，交付完整结构稿，不停在提纲或再次访谈；上下文已明确的用户、页面和任务不重问。
- 需求尚在探索时，围绕关键缺口共同澄清；已知部分先形成草稿，不强制选择模式或走固定问卷。
- 用户补充或纠正时，更新同一份结构稿中受影响的三问答案、区域和验收，保留未受影响的决定。询问或倾向不当成确认，被新决定替代的旧方案不混回当前稿。

对既有项目，在依赖当前能力作结构决策前，从目标入口追踪页面渲染、事件处理、数据来源与权限，并核对相关配置和测试。确认决策所需字段由真实生产者提供，不把类型声明或 mock 当成数据可用的证明。记录工作区、分支/提交与相关未提交改动、关键路径和未覆盖边界；只检查相关链路，不做全仓巡检。沿用项目领域术语，尊重相关架构决定和已确认约束，不另造对象、状态或动作名称。

区分三种内容：**源码已实现什么、用户现在希望改变什么、当前建议如何组织页面**。旧文档与源码不符时查证实现；新要求尚未实现时列为目标差异，不用旧实现否定用户目标。源码证据不等于部署状态，读取本地代码不授权访问生产。

代码不可访问时标记依赖它的结论待核验，继续整理不依赖代码的部分；新项目无代码则注明从需求设计。已有聊天和代码能补齐的问题自行补齐，只有影响主任务、结构或验收且无法查证的缺口才询问。

## 1. 页面定型

结合已核查的源码和可用实际页面，先用用户视角说明具体困难与目标变化：用户现在在哪一步找不到、看不懂、无法比较或不知道如何继续；方案实施后会怎样完成同一任务。不能只写“优化体验”或“换成表格”。无现有页面时描述目标场景，不编造现状；只有源码时不声称见过界面。

用一句话写任务契约：**谁，在什么情境下，针对什么对象，依据哪些信息，作出什么判断或动作，怎样知道完成了。**

选择页面骨架前，必须逐项回答以下三个问题，并在交付稿开头显式呈现；不能只用一句任务契约或组件名称代替：

1. **用户打开页面时，最重要的是看到什么？** 指出具体主信息、它为何优先，以及用户首先应看懂的事实或状态。
2. **为了理解这件主信息，还要看到哪些关联资源、关联模型和上下文？** 说明它们与主信息的关系、如何影响理解或判断；区分必须同时可见的依据与可按需查看的背景。
3. **用户看完后要作出什么反应、执行什么动作，或者继续思考什么？** 说明预期判断、操作或后续问题，以及页面如何支持它。结果可以是理解、比较、决定暂不行动或继续调查，不必强造一个按钮。

无法回答的部分明确写出缺失事实、暂定假设或需要澄清的问题，不用空泛结论补齐。

区分用户提供的事实、当前实现和设计假设。目标不清且会改变主结构时提出一个聚焦问题；其余部分继续。API 有字段不代表用户需要看到它；缺少决策数据时写明缺口，不用布局掩盖。

先判断任务能否融入现有页面。需要独立定位、持续处理、共享或足够空间时才建立新页面。确定一个主任务和主信息模型，辅助内容围绕它安排；有多个独立目标时按任务拆分，或有依据地提供视图切换。

按用户需要读出的关系选择骨架：

| 用户要完成的判断 | 首选结构 | 容易误选的情况 |
| --- | --- | --- |
| 对照多条记录的同一组字段 | 表格 | 只需识别和进入对象时列表即可 |
| 搜索或发现资源 | 目录、列表和筛选 | 图片决定识别时改用卡片网格 |
| 理解一个对象并操作 | 分区详情 | 不把历史、关系和属性混成字段堆 |
| 沿归属层级定位 | 树与路径 | 多种关系不硬塞成单一父子树 |
| 查依赖或受影响对象 | 关系列表 | 路径或传播本身影响判断时才用图 |
| 推进对象经过业务阶段 | 看板或阶段工作区 | 仅按负责人分组不是阶段流转 |
| 完成有先后依赖的输入 | 分步向导 | 简单输入用分组表单 |
| 追查已经发生的事情 | 事件时间线 | 当前流程位置和未来步骤另用阶段表达 |
| 查时间占用与资源冲突 | 日历或排期 | 只有日期无法证明占用和冲突 |
| 查异常、趋势及原因 | 状态墙或仪表盘并下钻 | 指标不能成为无任务的装饰 |
| 连续处理一批对象 | 队列加主从工作区 | 偶尔查详情不必常驻多个面板 |
| 读文档、讨论或版本变化 | 正文、讨论线程或差异比较 | 保留各自语义，不统一改成详情卡片 |
| 配置规则及适用范围 | 分组表单或规则矩阵 | 先表达约束和效果，再决定控件 |

选骨架时就写出验证其价值的任务：给定哪些信息，用户应能判断什么、做成什么。例如“同时比较三项任务的负责人，无需逐条打开详情”，而非“渲染出表格”。优先复用项目已有的用户行为测试入口或集成测试边界，选择能发现本次回归的最高合适层级；组件内部结构不作产品验收依据，不为凑数量增加测试入口。

通常给一个推荐方案，并说明为何它直接服务主任务。确有竞争方案时比较最相关的一项，不为展示完整性增加多视图。用户指定的结构若不利于任务，说明具体代价和建议，保留用户最终选择。

## 2. 信息编排

将推荐结构落实成按阅读顺序排列的区域，区域写业务名称，不写泛泛的“信息卡片”。每个区域说明：回答的问题、必要内容、动作、完成或失败的反馈。需要同时比较的值放在稳定位置，判断依据与操作保持邻近。

为每项信息确定展示层级：默认可见、展开可见、跳转查看或不展示。能够改变当前决定的信息不能藏入低频层；同一事实保留明确的权威位置，其他位置仅作有意义的摘要或入口。压缩无关信息而非一律缩字号。

明确用户从哪里进入、如何定位对象、在哪里判断和操作、结束后去哪里。返回时保留哪些筛选、排序、选择和草稿；需要分享或刷新恢复的状态优先沿用项目 URL 机制，敏感值不写入 URL。全局范围、页面导航和局部切换分别承担不同职责。

按当前操作补齐相关状态：加载、确实无数据、筛选无匹配、无权限、失败、提交中、完成；批处理另列部分成功及失败项恢复。状态必须区分未知与零，异步更新需说明是否陈旧。数据或权限规则不明时记录待确认项，不自行发明。

仅当进入实现范围时映射组件：沿用已有布局、组件库和设计规范，优先复用现有能力。拖动等交互提供键盘等价入口；关键状态有文字语义，不能仅依赖颜色。保留现有授权校验与数据契约。

## 3. 任务验收

用具体输入走主任务及相关关键例外，覆盖已明确的不同使用场景，不机械扩成长篇用户故事。每项核心验收写明输入/前置条件、可观察结果、验证方式和未执行边界，并对应三问：

- 主信息：用户能否找到并理解优先事实或状态。
- 关联信息：依据是否足够、便于对照，不需要跨页面记忆、拼接或猜测。
- 反应与行动：能否完成预期判断或操作，或明确下一步需调查什么；有操作时检查反馈与上下文恢复。

发现问题时定位责任层：选错信息关系就重选骨架；信息分散就调整编排；交互失效就修实现。不要用加卡片、换配色来修复任务结构。

设计阶段交付可执行的验收步骤和预期结果，不写“实测通过”。实现阶段按项目要求检查，并在实际界面验证受影响流程、窄屏和键盘操作。只有截图不能证明操作成功；工具或环境缺失时明确未验证项。

## 交付格式

默认在会话中给出可独立阅读的结构稿；用户要求保存或已有保存授权时更新同一份文档，沿用项目文档目录，无约定时可保存为 `docs/designs/<page>-structure.md`。不为每轮讨论另建版本；小问题直接回答。

1. **三问回答与任务契约**：逐项回答页面定型中的三个问题，再列主任务、对象、成功条件、观察范围、证据和假设。
2. **用户问题、目标变化与结构决策**：说明当前困难、改后如何完成任务、推荐骨架及取舍；分清已确认决定、建议和数据缺口。核查证据附源码位置与版本，结构约定用业务概念表达，不与易变文件布局绑死。
3. **区域顺序表**：`顺序 / 业务区域 / 用户问题 / 内容与依据 / 动作与反馈 / 展示层级`。空间关系不易用表说明时补一个低保真线框。
4. **任务路径与状态**：进入到完成的路径，以及上下文保持、权限和失败处理。
5. **验收与边界**：三问对应的输入、可观察结果、验证入口及实际证据或未验证标记；列出范围外事项、关键未决问题及其影响。

成稿或交接前，用未参与聊天的实现者视角检查：不翻对话也能理解目标用户、问题、三问答案、结构取舍、行为边界与验收。移除“按之前说的”等依赖聊天的指代，排除已被替代的决定；缺口就地标记，不把成稿等同于已确认、可实施或已验收。不自动创建 Issue、添加就绪标签或启动开发。

输出需让实现者知道“把什么放在哪里、为什么、如何验收”，而非只有原则或组件名。调用例：`$to-page 结合刚才的讨论和当前源码，整理这个页面的信息结构方案。`
