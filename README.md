# liuxie-skills

**和 AI 一起，把想法做成产品。**

面向非技术背景的产品创造者，两个 Skills：**PRDflow** 帮你把需求想清楚，**Devflow** 帮你把需求做出来。

从一个具体问题开始：你想为谁做什么，他们现在遇到了什么困难。你负责目标、取舍和体验，AI 帮你整理需求、设计方案、编写代码和检查结果。

## 两个 Skills，一条产品路径

### PRDflow · 把想法变成清楚的需求

有一个模糊想法，可以从讨论开始；已经聊过很多，也可以直接整理成稿。需求变化时，继续修改同一份文档。

PRDflow 帮你回答：

- **给谁用？** 用户遇到了什么问题，为什么需要这个产品。
- **怎样用？** 用户从哪里开始，经过哪些操作，最后得到什么。
- **先做什么？** 第一版的范围，以及这次暂时不做的事情。
- **怎样算做成？** 用哪些具体操作判断结果符合预期。

产出是一份可以阅读、讨论和验收的产品需求文档（PRD）。尚未确定的事情会明确标出，留给你继续判断。 已明确且影响产品行为的技术约束会保留来源，验收会说明从哪里触发、在哪里观察结果；详细实现设计交给 Devflow。

[查看 PRDflow](skills/prdflow/SKILL.md)

### Devflow · 把需求推进到可以验证的实现

带着确认过的需求开始开发，也可以从已有设计或改动继续。

```text
澄清目标 → 保存设计 → 优化设计 → 实现功能 → 审查结果
```

这五步既可以组成完整流程，也可以单独使用。例如，先讨论方案，或只审查已经写好的代码。保存和优化设计时，先读相关代码、核对当前行为与现有能力，再把方案收敛到满足验收的最小范围；设计优化会收集四份独立建议，再结合目标和代码证据判断哪些值得采纳。

Devflow 用六条核心规则约束目标、代码事实、阶段确认、改动范围、业务验收和交付边界。完整流程的每一步（包括返工）都会展示结果并等你确认后再推进；配置能保存、测试能通过，还须证明真实入口的业务结果符合约定。

[查看 Devflow](skills/devflow/SKILL.md)

## 从你的第一个小产品开始

下面以 Codex 为例。Skill 是交给 AI 的工作指南，需要在支持 Skills、能读写项目文件和运行命令的工具中使用。

### 1. 安装

在 Codex 对话中发送：

```text
$skill-installer 从 https://github.com/liuxie066/liuxie-skills 的 main 分支安装
skills/prdflow 和 skills/devflow 两个 Skill。
如果已有同名项，先核对版本，不要直接覆盖。
```

安装后在下一轮对话中使用；若没有出现，重启 Codex 后再试。 Skill 安装不包含其调用的本地程序及 API 凭据，已有环境可直接复用。详见 [OpenAI 官方安装说明](https://learn.chatgpt.com/docs/build-skills)。只需要梳理需求时，也可以先安装 PRDflow。

### 2. 说出你想解决的问题

在 Codex 中打开用于存放产品的项目文件夹，然后发送自己的想法。下面是一个练习示例：

```text
$prdflow 我想做一个自己用的内容选题工具。
我经常把想法记在不同地方，写内容时又找不到。
第一版希望能新增选题、标记待写或已完成，并按状态筛选。
我不懂编程，请用容易理解的话，和我一起明确需求与验收方法。
```

围绕草稿讨论和修改。确认符合你的想法后，再让 AI 保存：

```text
这份需求已确认，请保存到 docs/prd.md。
```

### 3. 开始做，并亲自试用

```text
$devflow 按 docs/prd.md 推进第一版的设计、实现和审查。
请先建议合适的流程，解释需要我决定的事项。
完成后告诉我怎样运行、测试了什么，还有什么没做完。
```

Devflow 会根据项目情况建议简单或完整流程，由你选择。两种流程都保留设计优化、实现验证和审查。

拿到结果后，按需求亲自试用：新增一个选题、改成已完成、切换筛选条件。如果约定了保存，再关闭并重新打开，看看内容和状态是否还在。遇到不符合预期的地方，把操作过程和实际结果交给 AI 继续处理。

**完成的标准，是你能用它做好约定的事情。**

## 适用范围

可以从个人网站、内容工具、报名页面或工作中的小工具起步，先完成一个有用的版本，再根据实际使用改进。

PRDflow 负责需求，Devflow 负责研发；产品是否上线、使用哪些付费服务、授予哪些账号权限，仍由你决定。Devflow 的四路设计优化需要工具支持多代理协作；具体项目的依赖和运行条件由 AI 核查，未完成的验证应明确说明。

## 网页信息结构

## 类型化决策

[jev-choice](skills/jev-choice/SKILL.md) 把 TypeSafe 的 Jev 当成本地判断客户端：一次请求提交多个 `choice` / `score` / `noul` 问题，拿回结构化答案、概率与置信度，并按**请求**在本地校验响应后才交给调用方——类型化输出保证的是接口，不是事实，所以它同时写明"不要过度信任"的边界。适合答案取值范围事先已知的判断（分类、路由、打分、排序、二值判定）；计数、算术、日期比较、事实检索与文本生成不适用。这是**可执行客户端**，API 设计指导与 cookbook 仍以 TypeSafe 官方的 `typesafe-ai` skill 为准。

2026-09-19 本机发现与加载检查通过（Claude 会话内可见并可自动触发）；脚本在两版 Python（3.12 / 3.9）下编译通过，本地拒绝矩阵 12/12、本地夹具矩阵 17/17（覆盖 401/403、422 列表型 detail、429 退避、307 明文降级拒绝、NaN 与重复键响应、非 argmax、概率和漂移等）。**真实端点已验证**：2026-09-19 首次接上凭据跑通，`choice` / `score` / `noul` 三种题型共 8 个问题全部通过本地校验、零致命错误、零建议级警告，解析出的模型版本为 `jev-1.13.0`；置信度闸门在一个真正未决的答案上如期触发，而 `ok` 仍为 true。失败路径（401/403/422/429/529）只在本地夹具上验过，未打真实端点。Pi 与 Hermes 仅确认文件就位，未验证其加载。

## 仓库文档与提交前检查

[repo-doc-hygiene](skills/repo-doc-hygiene/SKILL.md) 在修改或审阅软件仓库文档、注释和用户文案时核对事实来源、归属与行为语义；[pre-push-checks](skills/pre-push-checks/SKILL.md) 在推送或交付审查前核对实际改动范围、相关测试和项目必需检查。两者可自动调用；项目专有的数据来源和命令仍由项目规则定义。
